# Maven 使用规范

Maven 的配置文件看似很复杂，其实只需要根据项目的实际背景，设置个别的几个配置项而已。Maven 有自己的一套默认配置，使用者除非必要，并不需要去修改那些约定内容。这就是所谓的“**约定优于配置**”。

# 1 变量规范

## 1.1 系统变量

除了在 settings.xml 以及 pom.xml 当中用 properties 定义的常量，Maven 还提供了一些隐式的变量，用来访问系统环境变量。

- 内置属性
  - `${basedir}` 表示项目根目录，即包含 pom.xml 文件的目录
  - `${version}` 表示项目版本（Maven 3 中已不推荐，建议使用 `${project.version}`）
  - `${project.basedir}` 同 `${basedir}`
  - `${project.baseUri}` 表示项目文件地址
  - `${maven.build.timestamp}` 表示项目构建开始时间
- settings 属性
  - `${settings.localRepository}` 表示本地仓库路径
- POM 属性
  - `${project.build.directory}` 表示构建输出目录，默认为 target
  - `${project.build.sourceEncoding}` 表示主源码的编码格式
  - `${project.build.sourceDirectory}` 表示主源码路径
  - `${project.build.finalName}` 表示输出文件名称
  - `${project.version}` 表示项目版本，与 `${version}` 相同
- Java 系统属性
  - `${user.home}` 表示用户目录
  - `${java.version}` 表示 Java 版本
- 环境变量属性
  - `${env.JAVA_HOME}` 表示 JAVA_HOME 环境变量的值
  - `${env.HOME}` 表示用户目录

## 1.2 本地用户设定

用户的 settings.xml 中的所有设定都可以通过 `settings.` 前缀进行引用，如：

- `${settings.localRepository}` 代表用户的本地仓库目录

## 1.3 环境变量

系统的环境变量通过 `env.` 前缀引用：

- `${env.M2_HOME}`：Maven 安装路径
- `${java.home}`：Java 安装路径（严格来说这是 Java 系统属性，不需要 `env.` 前缀）

## 1.4 Java 系统属性

所有 JVM 中定义的 Java 系统属性都可以直接引用。

## 1.5 上级工程的变量

上级工程的 pom 中的变量用前缀 `${project.parent}` 引用。

上级工程的版本也可以这样引用：`${parent.version}`。

# 2 目录规范

Maven 默认的文件存放结构如下：

- /项目目录
  - pom.xml 用于 Maven 的配置文件
  - /src 源代码目录
    - /src/main 工程源代码目录
      - /src/main/java 工程 Java 源代码目录
      - /src/main/resources 工程的资源目录
    - /src/test 单元测试目录
      - /src/test/java
      - /src/test/resources
  - /target 输出目录，所有的输出物都存放在这个目录下
    - /target/classes 编译之后的 class 文件

每一个阶段的任务都知道怎么正确完成自己的工作，比如 compile 任务就知道从 src/main/java 下编译所有的 Java 文件，并把它输出的 class 文件存放到 target/classes 中。

对 Maven 来说，采用“约定优于配置”的策略可以减少修改配置的工作量，也可以降低学习成本，更重要的是，给项目引入了统一的规范。

# 3 版本规范

Maven 有自己的版本规范，一般是如下定义：

`<major version>.<minor version>.<incremental version>-<qualifier>`

比如 1.2.3-beta-01。要说明的是，早期 Maven（2.x）判断版本的算法是 major、minor、incremental 部分用数字比较，qualifier 部分用字符串比较，所以要小心 alpha-2 和 alpha-15 的比较关系，最好用 alpha-02 的格式。Maven 3 改用 ComparableVersion 算法，qualifier 中的数字部分也会按数值比较，不过统一位数仍是个好习惯。

Maven 在版本管理的时候可以使用几个特殊的字符串：**SNAPSHOT**、**LATEST**、**RELEASE**。

比如“1.0-SNAPSHOT”。各个部分的含义和处理逻辑如下说明：

## 3.1 SNAPSHOT

如果一个版本包含字符串 SNAPSHOT，Maven 就会在将这个组件发布（deploy）到远程仓库的时候将该符号展开为一个日期和时间值，转换为 UTC 时间。例如，“1.0-SNAPSHOT”会在 2020 年 5 月 5 日下午 2 点 10 分发布的时候变成 1.0-20200505.141000-1。

这个词只能用于开发过程中，因为一般来说，项目组都会频繁发布一些版本，最后实际发布的时候，会在这些 snapshot 版本中寻找一个稳定的，用于正式发布，比如 1.4 版本发布之前，就会有一系列的 1.4-SNAPSHOT，而实际发布的 1.4，也是从中拿出来的一个稳定版。

## 3.2 LATEST

指某个特定构件的最新发布，这个发布可能是一个发布版，也可能是一个 snapshot 版，具体看哪个时间最后。

## 3.3 RELEASE

指最后一个发布版。

需要注意的是，Maven 3 起已不再支持在插件版本中使用 LATEST 和 RELEASE，在依赖中也不推荐使用，因为它们会导致构建结果不可重复。
