# 雪花算法

# 1 引言

## 1.1 分布式 ID 的常见方案

当前主流的系统架构多采用分布式与微服务模式，数据量增长也催生了分库分表。进行水平分表后，需要保证各分片中 ID 的全局唯一性。

对于 MySQL 而言，表的主键 ID 一般采用自增的方式，但是水平分表之后，多张表会各自生成重复的 ID 值。那么如何保证水平分表后多张表中的 ID 全局唯一呢？

如果仍借助数据库主键自增的形式，可以为不同的表设置不同的初始值，然后按指定的步长自增。例如有 3 张拆分表，初始主键值分别为 1、2、3，自增步长为 3。这种方式的缺点是扩容时需要重新规划初始值和步长，而且依赖数据库的可用性。

也有人使用通用唯一识别码（UUID）作为主键，但常用的 UUID v4 是一个随机、无序的字符串（标准格式为 36 个字符），而 MySQL（InnoDB）推荐使用递增的数值类型作为主键，无序主键会导致 B+ 树频繁页分裂，因此并不适合。RFC 9562 于 2024 年标准化的 UUID v7 引入了时间有序性，可以缓解这一问题，但其 128 位的长度仍大于 64 位的 `long`。

还可以利用 Redis 自增命令的原子性来生成唯一 ID。这种方案实现直接，但每次生成 ID 都会产生网络 I/O，并且强依赖 Redis 的持久化、复制与故障切换策略；如果故障切换后的计数值发生回退，就可能生成重复 ID。因此，是否采用需要结合吞吐量、可用性和运维能力综合判断。

当然还有其他解决方案，不少互联网公司也有自己内部的实现。雪花算法是其中一种用于生成分布式 ID 的高效方案，也被许多互联网公司广泛采用。

Sonyflake 是索尼开源的一种雪花算法变体，默认使用 39 位记录以 10 毫秒为单位的时间差、8 位记录序列号、16 位记录机器码，理论使用期限约为 174 年，最多可区分 `2¹⁶` 个机器码，单个实例每 10 毫秒最多生成 256 个 ID。更多的机器码位并不意味着它天然适合动态 Pod：Sonyflake 默认取私有 IP 的低 16 位作为机器码，在 Kubernetes 等地址可能复用的环境中仍需自定义机器码分配与冲突校验策略。

## 1.2 雪花算法的 ID 结构

> 雪花算法（Snowflake）是 Twitter（2023 年已更名为 X）于 2010 年开源的一种算法，用于在分布式、高并发环境中生成趋势递增的 64 位 ID。

64 位 ID 的构成如下图所示：

![](imgs/1.png)

* 最高 1 位为符号位，固定为 0。因为生成的 ID 是正整数，如果是 1 就是负数了。
* 接下来 41 位存储毫秒级时间戳（当前时间与自定义起始时间之差），`2⁴¹ / (1000 × 60 × 60 × 24 × 365) ≈ 69.7`，**大约可以使用 69 年**。
* 再接下来 10 位存储机器码，包括 5 位 `datacenterId` 和 5 位 `workerId`，**最多可以部署 `2¹⁰ = 1024` 个节点**。
* 最后 12 位存储序列号。时间戳相同（同一毫秒）时，通过这个递增的序列号来区分。即对于同一个节点而言，**同一毫秒内可以生成 `2¹² = 4096` 个不重复的 ID**。

可以将雪花算法作为一个单独的服务进行部署，需要全局唯一 ID 的系统请求雪花算法服务获取 ID 即可。

对于每一个雪花算法服务，需要先指定 10 位的机器码，根据自身业务进行设定即可，例如“机房号 + 机器号”“机器号 + 服务号”，或者其他能够区分各节点的 10 位整数值。需要注意的是，同一时刻不能有两个节点使用相同的机器码，否则会生成重复 ID。

# 2 算法实现

```java
public class IdWorker {
    private static final long TWEPOCH = 1288834974657L;
    private static final int WORKER_ID_BITS = 5;
    private static final int DATACENTER_ID_BITS = 5;
    private static final int SEQUENCE_BITS = 12;

    private static final long MAX_WORKER_ID = ~(-1L << WORKER_ID_BITS);
    private static final long MAX_DATACENTER_ID = ~(-1L << DATACENTER_ID_BITS);
    private static final long SEQUENCE_MASK = ~(-1L << SEQUENCE_BITS);

    private static final int WORKER_ID_SHIFT = SEQUENCE_BITS;
    private static final int DATACENTER_ID_SHIFT = SEQUENCE_BITS + WORKER_ID_BITS;
    private static final int TIMESTAMP_LEFT_SHIFT = SEQUENCE_BITS + WORKER_ID_BITS + DATACENTER_ID_BITS;

    private final long workerId;
    private final long datacenterId;
    private long sequence;
    private long lastTimestamp = -1L;

    public IdWorker(long workerId, long datacenterId) {
        if (workerId > MAX_WORKER_ID || workerId < 0) {
            throw new IllegalArgumentException(
                    String.format("workerId must be between 0 and %d", MAX_WORKER_ID));
        }
        if (datacenterId > MAX_DATACENTER_ID || datacenterId < 0) {
            throw new IllegalArgumentException(
                    String.format("datacenterId must be between 0 and %d", MAX_DATACENTER_ID));
        }
        this.workerId = workerId;
        this.datacenterId = datacenterId;
    }

    public synchronized long nextId() {
        long timestamp = currentTimeMillis();
        if (timestamp < lastTimestamp) {
            throw new IllegalStateException(String.format(
                    "Clock moved backwards by %d milliseconds", lastTimestamp - timestamp));
        }

        if (timestamp == lastTimestamp) {
            sequence = (sequence + 1) & SEQUENCE_MASK;
            if (sequence == 0) {
                timestamp = waitUntilNextMillis(lastTimestamp);
            }
        } else {
            sequence = 0L;
        }

        lastTimestamp = timestamp;
        return ((timestamp - TWEPOCH) << TIMESTAMP_LEFT_SHIFT)
                | (datacenterId << DATACENTER_ID_SHIFT)
                | (workerId << WORKER_ID_SHIFT)
                | sequence;
    }

    private long waitUntilNextMillis(long timestamp) {
        long currentTimestamp = currentTimeMillis();
        while (currentTimestamp <= timestamp) {
            currentTimestamp = currentTimeMillis();
        }
        return currentTimestamp;
    }

    private long currentTimeMillis() {
        return System.currentTimeMillis();
    }
}
```

上述代码中，`TWEPOCH = 1288834974657L` 对应 UTC 时间 2010-11-04 01:42:54.657，是 Twitter 原始实现所用的起始时间；41 位时间差从该时刻起约可使用 69.7 年，也就是到 2080 年左右。自行实现时一般将起始时间设为系统上线前的某个时刻，以充分利用时间位。各部分的左移位数与 ID 结构一一对应：`workerId` 左移 12 位，`datacenterId` 左移 `12 + 5 = 17` 位，时间差左移 `12 + 5 + 5 = 22` 位。

其实雪花算法每一部分占用的比特位数并不是固定不变的。例如业务的生命周期可能达不到 69 年之久，那么可以减少时间差占用的位数（如 39 位毫秒级时间差约可使用 17 年）；如果雪花算法服务需要部署的节点超过 1024 个，那么可以把减少的位数补充给机器码。

对于机器码，可以根据自身情况做调整，例如机房号、服务器号、业务号、机器 IP 等都可以使用，只要部署的各个雪花算法服务最终计算出来的机器码能够区分开即可。

# 3 算法改进

## 3.1 雪花算法的优缺点

雪花算法有很多优点：

* 在高并发分布式环境下生成不重复的 ID，单个节点理论上每秒可生成约 409.6 万（`4096 × 1000`）个 ID。
* 基于时间戳以及同一时间戳下的序列号自增，单个节点内 ID 严格递增，全局范围内趋势递增。
* 不依赖第三方库或者中间件。
* 算法简单，在内存中计算，效率高。

但是，雪花算法也有一个严重的缺点：**依赖服务器时间，服务器时钟回拨时可能会生成重复 ID**。时钟回拨通常由网络时间协议（NTP）同步校时、闰秒处理或人工修改系统时间等引起。前面的实现在检测到回拨时直接抛出异常、拒绝服务，虽然保证了不重复，却牺牲了可用性。

为了避免时钟回拨导致的错误，需要对算法进行改进。

基础设施层可以通过 PTP、chrony 等方案提高节点间的时钟同步精度，并通过禁止大幅度阶跃、优先平滑校时来降低时钟回拨的概率，但这不能替代应用层的回拨检测。在容器和虚拟机环境中，系统时间通常仍受宿主机影响；在 Serverless 场景中，函数实例生命周期短，本地保存的 `lastTimestamp` 和机器码也不稳定。此类场景更适合使用独立的分布式 ID 服务，或者由外部协调系统以租约方式分配机器码，并在实例失效后延迟回收，避免不同实例同时使用同一机器码。

## 3.2 改进方案一：利用空闲的序列号区间

首先，雪花算法的末尾 12 位是序列号，用来区分同一毫秒内产生的不同 ID，同一毫秒总共可以产生 4096 个 ID，每一毫秒的序列号都从基础序列号 0 开始递增。假设业务系统在单机上的每秒请求数（QPS）为 3 万，那么平均每毫秒只需要产生 30 个 ID，远没有达到设计上限 4096，也就是说通常情况下序列号的使用都处在低水位，当发生时钟回拨时，这些尚未被使用的序列号就可以派上用场了。

因此，可以对基础序列号稍加修改，每发生一次时钟回拨，就将基础序列号加上指定的步长。例如开始时从 0 递增，发生一次时钟回拨后从 1024 开始递增，再发生一次则从 2048 开始递增，以此类推，这样最多能够容忍 3 次回拨到同一时间点（4096 个序列号被划分为 4 个区间，第 4 次回拨时 `basicSequence` 达到 4096，归零并等待下一毫秒）。该方案的前提是每毫秒实际使用的序列号不超过步长 1024，否则不同区间的序列号可能重叠。

```java
private static final long STEP_SIZE = 1L << 10;
private long basicSequence = 0L;

private long handleMovedBackwards(long currentTimestamp) {
    basicSequence += STEP_SIZE;
    if (basicSequence > MAX_SEQUENCE) {
        basicSequence = 0L;
        currentTimestamp = waitUntilNextMillis(lastTimestamp);
    }
    sequence = basicSequence;
    lastTimestamp = currentTimestamp;
    return ((currentTimestamp - START_TIMESTAMP) << TIMESTAMP_LEFT)
            | (workerId << WORKER_ID_LEFT)
            | sequence;
}
```

> 注：该片段中的机器码 `workerId` 占满 10 位，不再拆分为 `datacenterId` 和 `workerId`，与第 2 章的实现略有不同。

## 3.3 改进方案二：启用备用 workerId

如果上面的解法还是不足以满足要求，还有一种更彻底的解法。

雪花算法给 `workerId` 预留了 10 位，即 `workerId` 的取值范围为 `[0, 1023]`。事实上，实际生产环境不大可能需要部署 1024 个分布式 ID 服务，所以可以将 `workerId` 的取值范围缩小为 `[0, 511]`，把 `[512, 1023]` 这个范围的 `workerId` 当作备用 `workerId`：`workerId` 为 0 的备用 `workerId` 是 512，`workerId` 为 1 的备用 `workerId` 是 513，以此类推。

具体逻辑是：若回拨时间不超过阈值 `MAX_BACKWARD_MS`，则等待系统时间追上；若回拨过多，则切换到备用 `workerId`，并检查该 `workerId` 上一次生成 ID 的时间。两个 `workerId` 的 ID 空间互不重叠，但切换时仍必须保证当前时间严格晚于备用 `workerId` 的最后使用时间，否则还可能复用相同的时间戳和序列号。下面的代码参考 Apache ShardingSphere 早期的雪花主键生成器，并加入备用 `workerId` 处理：

```java
private static final long WORKER_ID_HALF_RANGE = 1L << (WORKER_ID_BITS - 1);
private static final Map<Long, Long> WORKER_ID_LAST_TIME = new ConcurrentHashMap<>();

@Override
public synchronized Number generateKey() {
    long currentMillis = System.currentTimeMillis();

    if (lastTime > currentMillis) {
        long backwardMillis = lastTime - currentMillis;
        if (backwardMillis <= MAX_BACKWARD_MS) {
            currentMillis = waitUntilTime(lastTime);
        } else {
            workerId = workerId >= WORKER_ID_HALF_RANGE
                    ? workerId - WORKER_ID_HALF_RANGE
                    : workerId + WORKER_ID_HALF_RANGE;

            long spareLastTime = WORKER_ID_LAST_TIME.getOrDefault(workerId, -1L);
            if (spareLastTime >= currentMillis) {
                throw new IllegalStateException(String.format(
                        "Clock moved backwards: spare workerId %d was last used at %d, current time is %d",
                        workerId, spareLastTime, currentMillis));
            }
            lastTime = spareLastTime;
        }
    }

    if (lastTime == currentMillis) {
        sequence = (sequence + 1) & SEQUENCE_MASK;
        if (sequence == 0L) {
            currentMillis = waitUntilTime(lastTime + 1L);
        }
    } else {
        sequence = 0L;
    }

    lastTime = currentMillis;
    WORKER_ID_LAST_TIME.put(workerId, lastTime);
    return ((currentMillis - EPOCH) << TIMESTAMP_LEFT_SHIFT_BITS)
            | (workerId << WORKER_ID_LEFT_SHIFT_BITS)
            | sequence;
}

private long waitUntilTime(long targetMillis) {
    long currentMillis = System.currentTimeMillis();
    while (currentMillis < targetMillis) {
        try {
            Thread.sleep(targetMillis - currentMillis);
        } catch (InterruptedException ex) {
            Thread.currentThread().interrupt();
            throw new IllegalStateException("Interrupted while waiting for the clock", ex);
        }
        currentMillis = System.currentTimeMillis();
    }
    return currentMillis;
}
```

等待结束后必须重新读取 `currentMillis`，不能继续使用回拨时取得的旧值。`System.nanoTime()` 适合测量同一进程内的时间间隔，但它不表示 UTC 时间，进程重启后基准也会变化，因此不能直接替代雪花算法中的毫秒时间戳。持久化历史最大时间戳可以辅助处理服务重启，但只有同步、可靠地写入持久化存储才能作为严格的防重保证，这会引入额外延迟和外部依赖。

# 4 总结

* 雪花算法用“1 位符号位 + 41 位时间差 + 10 位机器码 + 12 位序列号”拼成一个 64 位 `long`，无需依赖中间件即可在本地高效生成全局唯一、趋势递增的 ID；时间位约可使用 69 年，单个节点每毫秒最多生成 4096 个 ID。
* 各部分的位数可以按业务需要调整，但必须保证各节点的机器码不重复。Sonyflake 等变体正是通过重新分配时间、机器码和序列号位数来适配不同场景。
* 雪花算法最大的问题是依赖系统时钟，时钟回拨可能导致 ID 重复，可以通过短暂等待、预留序列号区间、切换备用 `workerId` 等方式缓解。时钟同步只能降低回拨概率，服务重启和机器码复用仍需通过持久化校验、租约或外部协调机制处理。
* 实际选型时也可以参考成熟的开源方案：美团 Leaf 提供数据库号段模式和 Snowflake 模式，后者借助 ZooKeeper 分配并在本地缓存 `workerId`；百度 UidGenerator 默认采用“1 位符号位 + 28 位相对时间差（秒）+ 22 位机器 ID + 13 位序列号”的结构，并通过 RingBuffer 预生成 ID；Apache ShardingSphere 也内置了 Snowflake 分布式主键生成算法。选型时应重点比较位分配、机器码管理、时钟回拨策略和外部依赖，而不能只看生成性能。
