# 缓存一致性与更新策略

# 1 为什么需要缓存

一般在项目中，最消耗性能的地方就是后端服务的数据库了。而数据库的读写频率常常是不均匀分布的，大多数情况下是读多写少，并且读操作还会带有一些复杂的条件，比如 `LIKE`、`GROUP BY`、`JOIN` 等，这些语法非常消耗性能，因此数据库很容易在读操作的环节遇到瓶颈。

那么通过给数据库加一个前置缓存，就可以有效地吸收不均匀的请求，抵挡流量波峰。

另外，如果应用与数据源不在同一台服务器上，中间还会有很多网络消耗，也会对应用的响应速度有很大影响。如果当前应用对数据实时性的要求不那么高，在应用侧加上缓存就能快速地提升效率。

# 2 更新策略

既然是缓存，就意味着缓存中暂存的数据只是个副本，相当于把数据存放了 2 份，一份存放在数据库中，另一份存放在缓存中。当有新的数据要写入或者旧数据需要更新的时候，如果我们只更新了其中一份数据源，两边的数据就会不一致。所以使用缓存必然要面对一个问题：缓存数据与数据库数据如何进行有效且快速的同步。

一般来说，缓存的更新策略有以下三种模式：

- 旁路缓存（Cache Aside）更新模式：由应用程序同时维护缓存和数据库，读时未命中则从数据库加载并回填缓存，写时先更新数据库再删除缓存。
- 读穿/写穿（Read/Write Through）更新模式：应用程序只与缓存交互，由缓存负责同步读取和更新数据库。
- 异步写回（Write Behind，又称 Write Back）更新模式：只更新缓存，由缓存定时异步批量更新数据库。

## 2.1 Cache Aside 更新模式

- 未命中：应用程序先从缓存取数据，没有得到，则从数据库中取数据，成功后放到缓存中。
- 命中：应用程序从缓存中取数据，取到后返回。
- 更新：先把数据存到数据库中，成功后再去删除缓存或者让缓存失效。

![](imgs/1.png)

这种策略下，在读写并发时（读请求未命中缓存的同时有写请求）仍可能出现脏数据的问题，具体推演见 3.4 节。

## 2.2 Read/Write Through 更新模式

应用程序只需要维护缓存，数据库的维护工作由缓存代理：

![](imgs/2.png)

### 2.2.1 Read Through

Read Through 模式就是在查询操作中更新缓存。也就是说，当缓存失效的时候，Cache Aside 模式是由调用方负责把数据加载到缓存，而 Read Through 模式则由缓存服务自己来加载，对应用程序透明。

### 2.2.2 Write Through

Write Through 模式和 Read Through 相仿，不过是在更新数据时发生。当有数据更新的时候，如果没有命中缓存，直接更新数据库，然后返回；如果命中了缓存，则更新缓存，然后由缓存自己更新数据库（这是一个同步操作）。

## 2.3 Write Behind 更新模式

Write Behind 更新模式就是在更新数据的时候，只更新缓存，不更新数据库，而缓存会异步地批量更新数据库。这个设计的好处是直接操作内存，速度快。因为是异步的，Write Behind 更新模式还可以把对同一个数据的多次操作合并后再写入数据库，所以性能的提升是相当可观的。

![](imgs/3.png)

但其带来的问题是，数据不是强一致的，而且可能会丢失：如果缓存节点在脏数据刷入数据库之前宕机，这部分尚未持久化的更新就会丢失。另外，Write Behind 更新模式的实现逻辑比较复杂，因为它需要跟踪哪些数据被更新了、哪些数据需要刷到持久层上。通常只有在缓存数据被淘汰或到达刷新周期时，才会把它真正持久化。

# 3 场景推演

以上的理论知识准备完毕，下面用具体场景推演一下缓存更新的细节问题。

理论是美好的，现实是残酷的，现实最终会把“美好”的理论变成“没好”的，不信走着瞧。

缓存怎么更新，在实际应用中有很多种做法，但是归根结底，就是当数据发生变化时如何考虑以下两个问题：

- 对缓存是删除，还是更新？
- 先操作数据库，还是先操作缓存？

组合起来有以下四种方案。

## 3.1 先更新数据库，后更新缓存

第一种场景：更新数据库成功，更新缓存失败，则出现缓存与数据库不一致。

第二种场景：请求 A 更新值为 99，请求 B 更新值为 98。

![](imgs/4.png)

- 请求 A 先发起，更新数据库为 99，但还没有来得及更新缓存。
- 请求 B 发起，更新数据库为 98，又更新了缓存值为 98。
- 请求 A 这时才更新缓存的值为 99。

这样数据库的值为 98，但缓存的值为 99，数据不一致出现了。

## 3.2 先更新缓存，后更新数据库

第一种场景：更新缓存成功，更新数据库失败，则出现缓存与数据库不一致。

第二种场景：与上面的流程类似，出现的问题也很类似。

- 请求 A 先更新缓存为 99，但还没有来得及更新数据库。
- 请求 B 更新缓存为 98，又更新了数据库为 98。
- 请求 A 这时才更新数据库为 99。

这样缓存的值为 98，数据库的值为 99，导致不一致。

## 3.3 先删除缓存，后更新数据库

第一种场景：删除缓存成功，更新数据库失败。此时缓存为空、数据库仍是旧值，下一次读请求发现缓存中没有数据，会从数据库重新加载旧值，缓存与数据库并不会出现不一致，因而影响不大。但即使数据库更新成功，也存在另一个问题：在旧缓存被删除后、数据库更新完成之前，这段时间内如果有读操作，旧值会被重新加载到缓存中，这就相当于没更新缓存（即下面的第二种场景）。

第二种场景：请求 A 更新值为 99，请求 B 获取值。

![](imgs/5.png)

- 请求 A 更新值，先把缓存中的值删除，但还没有来得及更新数据库。
- 此时请求 B 过来查询此值，发现缓存中不存在，就到数据库中查询。
- 请求 B 在数据库中获取到旧值 100，再把该值设置到缓存中。
- 请求 A 这时才更新数据库里面的值为 99。

这样就导致了缓存和数据库的不一致问题：数据库已是 99，而缓存中的值在过期之前一直是旧数据 100。

## 3.4 先更新数据库，后删除缓存

第一种场景：更新数据库成功，删除缓存失败，则出现缓存与数据库不一致。

第二种场景：请求 A 查询值，请求 B 更新值。

![](imgs/6.png)

- 请求 A 发起查询请求，此时缓存恰好失效，直接到数据库查询到 100，但还没有来得及去设置缓存。
- 请求 B 更新值，先更新数据库为 98，再删除缓存。
- 请求 A 这时才设置缓存为 100。

这样数据库的值为 98，而缓存中却是旧值 100，同样出现了不一致。

## 3.5 总结

推演完毕。

结果发现，没有一个方案走得通，这还怎么用？这么一看，现实不只把理论给打残了，而且是按在地上摩擦啊！

通过上面的推演，可以发现这些方案主要存在两种问题：

（1）第一种问题：**操作的原子性无法保证**

对数据库与缓存的操作是分两步操作的，并没有类似数据库事务那样的控制，一旦第一步成功，第二步失败，必然导致数据不一致。

（2）第二种问题：**并发请求导致数据覆盖**

并发环境下，多个请求的处理顺序无法保证，会导致旧数据覆盖掉新数据的情况。但是，并发不一定导致数据覆盖，这是一个概率问题，如何将概率降至最低，或者降为零（比如加锁），需要我们根据具体的业务场景来分析。

但是，**任何脱离实际业务的推演都是耍流氓**。

下面逐个分析。

### 3.5.1 先更新数据库，后更新缓存

相对来讲，理论上这种方式比“先更新数据库，后删除缓存”有着更高的读性能，因为它事先在缓存中准备好了数据。

但是缺点也很明显：

- 如果是一个写多读少的场景，采用这种方案可能会导致更新了十次缓存，但只读了一次，其余九次的更新是没必要的，浪费性能。
- 如果写入数据库的值并不是直接写入缓存的，而是要经过一系列复杂的计算再写入缓存，那么每次写入数据库后都重新计算写入缓存的值，同样是浪费性能的，这种情况下显然删除缓存更为适合。

从更一般的角度看，更新缓存还是删除缓存，主要取决于更新成本与一致性要求：

- 如果更新缓存的代价很小，可以更新缓存以维持较高的命中率，但必须规避 3.1 中并发写导致的旧值覆盖。除了加锁，还可以为数据携带单调递增的版本号，仅允许新版本覆盖旧版本。
- 版本号校验必须与写入原子执行；如果只是先读取版本号、再判断并写入，两个并发请求之间仍然存在竞态。以 Redis 为例，可以通过 Lua 脚本或事务式的条件更新完成原子比较与写入。
- 如果缓存需要经过复杂计算才能得到，通常更适合删除缓存，在下一次读取时按需重建。

### 3.5.2 先更新缓存，后更新数据库

既然我们将缓存视为数据库的副本，那么数据库就是单一事实来源，所有数据必须以数据库为准。“先更新缓存，后更新数据库”在数据库更新失败时会导致“缓存有新数据，而数据库没有”，这是绝对不能容忍的，所以该方案在实际业务当中基本没法用。

### 3.5.3 先删除缓存，后更新数据库

该方案的主要风险是：第一次删除缓存后，并发读请求从尚未更新的数据库读到旧值并将其回填。对此可以采用“**延迟双删策略**”，在数据库更新后再次删除这段时间内可能被回填的旧值：

- 先删除缓存。
- 再更新数据库。
- 等待一段时间后，再次删除缓存。

延迟双删主要用于修复“先删除缓存，后更新数据库”产生的并发旧值回填，并不能保证数据库更新与两次删除具备事务原子性。使用时还要注意以下问题：

1. **延迟时间如何确定**：不能固定写成 1 秒，应根据读路径的高分位耗时评估；如果采用读写分离，还要覆盖主从复制延迟，并结合监控数据留出余量。延迟过短可能删不到脏数据，过长则会扩大旧值可见窗口。
2. **如何避免阻塞业务线程**：不应让写请求同步休眠，通常通过延迟队列、MQ 或持久化任务异步执行第二次删除。
3. **第二次删除失败怎么办**：可以使用 MQ 重试、持久化任务表配合定时扫描等方式兜底。进程内线程或 `DelayQueue` 在进程重启后会丢失任务，只适合可靠性要求较低的场景；一致性要求不高时，也可以依赖较短的缓存过期时间最终修正。

延迟双删增加了时序参数和重试链路，只有业务确实无法接受不一致窗口时才值得采用。一般场景仍应优先使用“先更新数据库，后删除缓存”，并为缓存设置过期时间。

### 3.5.4 先更新数据库，后删除缓存

这种方案在实际业务当中使用率最高，原因有两点：

- 先更新数据库，首先保证了数据源头一定是正确的。
- 并发导致数据不一致的概率非常低。

回头看看上面的场景，如果发生不一致，需要同时具备以下四个条件：

- 读操作时，缓存恰好失效。
- 有一个并发的写操作。
- 写操作比读操作更快。
- 读操作早于写操作进入数据库，晚于写操作更新缓存。

而实际上数据库的写操作通常比读操作慢得多，而且可能还要锁行、锁表。读操作必须在写操作之前进入数据库，又要晚于写操作更新缓存，这些条件同时具备的概率并不大。并且即使出现这个问题，还可以设置缓存过期时间来自动兜底；对一致性要求更高的场景，也可以在此基础上叠加延迟双删。

但是该方案还有个问题要解决：第二步删除缓存失败怎么办？

答案是提供一个重试机制，比如借助 MQ：

![](imgs/7.png)

- 更新数据库数据。
- 缓存因为种种问题删除失败。
- 将需要删除的 key 发送至消息队列。
- 消费者获得需要删除的 key，再次执行删除。
- 删除仍然失败时按退避策略重试，并在超过重试上限后进入死信队列或交由人工处理。

删除缓存本身是幂等操作，适合重试。MQ 适合需要跨进程持久化、失败重投和消费确认的场景；规模较小的系统也可以使用持久化任务表加定时扫描。单纯使用进程内队列虽然实现简单，但进程重启会丢失任务。

然而，在业务代码中发送失效消息仍有侵入性，而且数据库事务提交与消息发送之间也可能出现不一致。另一种方案是订阅数据库的二进制日志（binlog），通过 Canal、Debezium 等 CDC 工具捕获已经提交的数据变更，再由独立消费者删除缓存。

![](imgs/8.png)

- 更新数据库数据，数据库将变更写入 binlog。
- CDC 工具读取 binlog，提取表、主键和变更类型等信息。
- 消费者根据业务规则计算缓存 key，并执行删除。
- 删除失败时将任务交给可靠队列重试。

CDC 降低了对业务代码的侵入，但并没有消除复杂度：需要维护表记录与缓存 key 的映射，处理重复事件、消费延迟和失败重试。失效消费者也应按幂等方式实现。

### 3.5.5 多级缓存的一致性

如果系统同时使用进程内 L1 缓存和 Redis 等共享 L2 缓存，只删除 L2 并不够，L1 中的旧值仍可能继续命中。常见做法是在数据库变更后删除 L2，并向各应用实例广播 L1 失效事件。

Redis Pub/Sub 可以实现低延迟广播，但它采用至多一次投递：订阅者断线或处理失败时，消息不会重放。因此，一致性要求较高时应使用支持持久化和消费确认的消息队列或 Redis Streams，并配合版本号、较短的 L1 过期时间或定期校准来处理漏消息。多级缓存可以进一步降低延迟，却也增加了失效传播链路，只有性能收益足够明显时才适合引入。

### 3.5.6 小结

- **方案 1**：先更新数据库，后更新缓存，**最好不用**。
- **方案 2**：先更新缓存，后更新数据库，**坚决不用**。
- **方案 3**：先删除缓存，后更新数据库，**适度使用**。
- **方案 4**：先更新数据库，后删除缓存，**推荐使用**。

但是也不能盲从，正所谓：具体问题，具体分析。

没有完美的方案，只有合适的方案。

# 4 主从架构下的问题

上面的各种场景都是只有一个数据库实例的情况，而实际生产环境中往往是一主多从的。如果缓存未命中后从从库回源，主从复制延迟会产生额外的旧值回填问题：

1. 写请求更新主库，并删除缓存。
2. 主库的变更尚未同步到从库。
3. 并发读请求发现缓存未命中，从从库读到旧值并写回缓存。
4. 即使从库随后完成同步，缓存中的旧值仍会保留到下一次删除或过期。

为了解决这种问题，可以考虑以下几种方案。

## 4.1 强制缓存读主数据库

缓存未命中时始终从主库加载数据，就不必考虑主从复制延迟，代价是主库的读压力会增大。对一致性要求高、缓存回源量可控的业务，这是最直接的方案。

## 4.2 选择性地读主数据库

只有在写操作后的短时间内，读从库才容易获得旧值，因此可以让刚更新过的数据暂时从主库回源，其他数据仍然从从库读取。

一种实现方式是在更新数据库时设置一个标记 key，格式为“缓存 key + 业务数据 ID”，其过期时间应覆盖主从复制延迟。在读的时候，首先判断是否存在标记 key：如果存在，则从主库加载数据到缓存；如果不存在，则从从库加载。标记过期时间同样应根据复制延迟监控确定，不能使用脱离实际环境的固定值。

## 4.3 订阅从库的 binlog

可以通过 Canal 等工具订阅从库的 binlog：当从库已经应用某项变更后，再删除对应缓存，此时后续回源从从库读到的就是新值。需要注意，从库必须启用二进制日志，并开启 `log_replica_updates`（MySQL 8.0.26 之前名为 `log_slave_updates`），才能把从复制源接收并应用的变更写入自身的 binlog。

## 4.4 延迟再次删除

也可以在更新主库并首次删除缓存后，异步延迟执行第二次删除，使时间覆盖常见的主从复制延迟。这种方案实现相对简单，但本质上依赖延迟参数，复制延迟突增时仍可能失效，因此要配合监控、可靠重试和缓存过期时间使用。

# 5 是否一定需要外部缓存

TiDB、CockroachDB、OceanBase 等 Distributed SQL 数据库能够提供水平扩展、分布式事务和副本一致性，但这并不意味着外部缓存已经没有必要。热点读、极低延迟、数据库成本隔离和流量削峰等场景仍可能从缓存中受益。

数据库能力增强后，更合理的做法是重新评估缓存的必要性：如果数据库已经满足延迟和吞吐量目标，省去缓存可以显著降低一致性复杂度；如果性能测试表明缓存收益明显，再选择与业务一致性要求匹配的更新策略。缓存不是默认必选项，也不是数据库扩展能力的替代品。

# 6 总结

| 策略 | 写操作 | 一致性 | 主要风险 | 适用场景 |
| --- | --- | --- | --- | --- |
| Cache Aside（先更新数据库，后删除缓存） | 应用更新数据库后删除缓存 | 最终一致，不一致窗口小 | 删除缓存失败、读写并发的小概率脏数据 | 绝大多数读多写少的业务，最常用 |
| Read/Write Through | 由缓存同步更新数据库 | 取决于缓存组件的实现 | 依赖组件支持，写延迟较高 | 有成熟缓存中间件、希望对应用透明的场景 |
| Write Behind | 只写缓存，异步批量刷库 | 弱 | 尚未刷库的数据可能丢失 | 写多且能够承受数据丢失风险的场景 |
| 先删除缓存，后更新数据库 | 删除缓存后更新数据库 | 读写并发易脏 | 旧值被回填到缓存 | 配合延迟双删适度使用 |
| 更新缓存类方案 | 写数据库与写缓存 | 并发写易覆盖 | 并发覆盖、浪费计算 | 更新代价小且能加锁或执行原子版本控制时 |

总体而言，缓存与数据库无法做到无代价的强一致，实际工程中一般选择“先更新数据库，后删除缓存”，并配合缓存过期时间、可靠重试或订阅 binlog 异步删除来保证最终一致。在主从和多级缓存架构下，还要分别处理复制延迟导致的旧值回填，以及 L1 失效消息漏投的问题。引入缓存前应先通过性能测试确认收益，避免为不必要的缓存承担一致性成本。
