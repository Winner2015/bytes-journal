# Redis 配置详解

进入 Redis 的安装包，里面的 `redis.conf` 就是默认的配置文件，启动 Redis Server 的时候，可以指定加载某个路径下的配置文件：`redis-server [path of configuration file]`。

> 说明：本文配置项及默认值以较新版本的 `redis.conf`（7.x/8.x）为准，旧版本中已改名或移除的配置项会单独注明。

默认的配置文件中，首先约定了存储单位：

```text
1k  => 1000 bytes
1kb => 1024 bytes
1m  => 1000000 bytes
1mb => 1024*1024 bytes
1g  => 1000000000 bytes
1gb => 1024*1024*1024 bytes
```

Redis 配置中对单位的大小写不敏感，`1GB`、`1Gb` 和 `1gB` 都是相同的。由此也说明，Redis 只支持 bytes，不支持 bit 单位。

Redis 支持以 `include` 的方式引入其他配置文件，7.0 起还支持通配符，比如：

```conf
include /path/to/local.conf
include /path/to/other.conf
include /path/to/fragments/*.conf
```

需要注意的是，假如同一个配置项在不同配置文件中都有定义，则以最后一行读入的为准，就是说**后面的配置项会覆盖前面的配置项**。

# 1 通用配置

默认情况下，Redis 并不是以 daemon 形式来运行的。通过 `daemonize` 配置项可以控制 Redis 的运行形式，如果改为 `yes`，那么 Redis 就会以 daemon 形式运行：

```conf
daemonize no
```

当以 daemon 形式运行时，Redis 会生成一个 pid 文件，默认会生成在 `/var/run/redis.pid`。当然，可以通过 `pidfile` 来指定 pid 文件生成的位置，比如：

```conf
pidfile /path/to/redis.pid
```

如果配置文件中没有 `bind` 配置项，Redis 会响应本机所有可用网卡的连接请求。Redis 允许通过 `bind` 配置项来指定要绑定的 IP，比如：

```conf
bind 192.168.1.2 10.8.4.2
```

新版本自带的 `redis.conf` 中默认为 `bind 127.0.0.1 -::1`，即只监听本机回环地址（`-` 前缀表示该地址不可用时也不影响启动）。另外，3.2 起新增了保护模式 `protected-mode`，默认开启：在默认用户没有设置密码的情况下，Redis 只接受来自本机（127.0.0.1、::1 或 Unix socket）的连接，以防止未设密码的实例直接暴露在公网上。

```conf
protected-mode yes
```

Redis 的默认服务端口是 6379，可以通过 `port` 配置项来修改。如果端口设置为 0 的话，Redis 便不会监听 TCP 端口了。

```conf
port 6379
```

可是，如果 Redis 不监听端口，还怎么与外界通信呢？其实 Redis 还支持通过 Unix socket 方式来接收请求。可以通过 `unixsocket` 配置项来指定 Unix socket 文件的路径，并通过 `unixsocketperm` 来指定文件的权限。

```conf
unixsocket /tmp/redis.sock
unixsocketperm 700
```

在高 QPS 的环境下需要提高 backlog 的值来避免客户端连接缓慢的问题。想要提高 backlog 的值，除了需要设置 Redis 的 `tcp-backlog`，还要同时调大 Linux 的相关配置，否则，Linux 内核会默认将其截取为 `/proc/sys/net/core/somaxconn` 的大小。

```conf
tcp-backlog 511
```

当一个客户端一直没有请求发向 server 端，那么 server 端有权主动关闭这个连接，可以通过 `timeout` 来设置“空闲超时时限”，0 表示永不关闭。

```conf
timeout 0
```

TCP 连接保活策略，可以通过 `tcp-keepalive` 配置项来进行设置，单位为秒。假如设置为 60 秒，则 server 端会每 60 秒向连接空闲的客户端发起一次 ACK 请求，以检查客户端是否已经失效，对于无响应的客户端则会关闭其连接，所以关闭一个连接最长需要 120 秒的时间。如果设置为 0，则不会进行保活检测。3.2.1 起默认值由 0 改为 300。

```conf
tcp-keepalive 300
```

Redis 支持通过 `loglevel` 配置项设置日志等级，共分四级，即 `debug`、`verbose`、`notice`、`warning`；7.2 起还增加了 `nothing`（不记录任何日志）。

```conf
loglevel notice
```

Redis 也支持通过 `logfile` 配置项来设置日志文件的生成位置。如果设置为空字符串，则 Redis 会将日志输出到标准输出。假如在 daemon 情况下将日志设置为输出到标准输出，则日志会被写到 `/dev/null` 中。

```conf
logfile ""
```

如果希望日志打印到 syslog 中，也很容易，通过 `syslog-enabled` 来控制。另外，`syslog-ident` 还可以指定 syslog 里的日志标志，比如：

```conf
syslog-ident redis
```

而且还支持指定 syslog 设备，值可以是 `USER` 或 `LOCAL0`～`LOCAL7`。具体可以参考 syslog 服务本身的用法。

```conf
syslog-facility local0
```

对于 Redis 来说，可以设置其数据库的总数量，假如希望一个 Redis 包含 16 个数据库，那么设置如下：

```conf
databases 16
```

这 16 个数据库的编号将是 0 到 15。默认的数据库是编号为 0 的数据库。用户可以使用 `SELECT <dbid>` 来选择相应的数据库。

# 2 快照配置

快照，主要涉及的是 Redis 的 RDB 持久化相关的配置。

`save <seconds> <changes>` 表示在指定秒数内，如果至少发生了指定次数的写操作，就触发一次持久化。举例来说：

```conf
save 900 1      # 900 秒（15 分钟）内至少有 1 个 key 发生改变，就触发一次持久化
save 300 10     # 300 秒（5 分钟）内至少有 10 个 key 发生改变，就触发一次持久化
save 60 10000   # 60 秒内至少有 10000 个 key 发生改变，就触发一次持久化
```

以上是旧版本 `redis.conf` 中的默认值。新版本（6.2 起）的默认值改为 `3600 1`、`300 100`、`60 10000`，7.0 起的配置文件中写作一行多组参数的形式：`save 3600 1 300 100 60 10000`。

如果想禁用 RDB 持久化的策略，只要不设置任何 `save` 指令就可以，或者给 `save` 传入一个空字符串参数也可以达到相同效果，就像这样：

```conf
save ""
```

如果用户开启了 RDB 快照功能，那么在 Redis 持久化数据到磁盘时如果出现失败，默认情况下，Redis 会停止接受所有的写请求。这样做的好处在于可以让用户很明确地知道内存中的数据和磁盘上的数据已经存在不一致了。如果 Redis 不顾这种不一致，一意孤行地继续接收写请求，就可能会引起一些灾难性的后果。

如果下一次 RDB 持久化成功，Redis 会自动恢复接受写请求。

当然，如果不在乎这种数据不一致或者有其他的手段发现和控制这种不一致的话，完全可以关闭这个功能，以便在快照写入失败时，也能确保 Redis 继续接受新的写请求。配置项如下：

```conf
stop-writes-on-bgsave-error yes
```

对于存储到磁盘中的快照，可以设置是否进行压缩存储。如果是的话，Redis 会采用 LZF 算法进行压缩。如果不想消耗 CPU 来进行压缩的话，可以设置为关闭此功能，但是存储在磁盘上的快照会比较大。

```conf
rdbcompression yes
```

在存储快照后，我们还可以让 Redis 使用 CRC64 算法来进行数据校验，但是这样做会在保存和加载 RDB 文件时增加大约 10% 的性能消耗，如果希望获取到最大的性能提升，可以关闭此功能。

```conf
rdbchecksum yes
```

我们还可以设置快照文件的名称，默认是这样配置的：

```conf
dbfilename dump.rdb
```

还可以设置这个快照文件存放的路径（AOF 文件也会存放在这个目录下），默认设置为当前工作目录：

```conf
dir ./
```

# 3 主从配置

Redis 提供了主从同步功能。

> 注意：5.0 起，主从相关配置项中的 `slave` 统一改为 `replica`（如 `slaveof` → `replicaof`、`slave-read-only` → `replica-read-only`），旧名称仍可作为别名使用。下文统一使用新名称。

通过 `replicaof` 配置项可以控制某一个 Redis 作为另一个 Redis 的从服务器，通过指定 IP 和端口来定位到主 Redis 的位置。一般情况下建议用户为从 Redis 设置一个不同频率的快照持久化的周期，或者为从 Redis 配置一个不同的服务端口等。

```conf
replicaof <masterip> <masterport>
```

如果主 Redis 设置了验证密码的话（使用 `requirepass` 来设置），则在从 Redis 的配置中要使用 `masterauth` 来设置校验密码，否则的话，主 Redis 会拒绝从 Redis 的访问请求。如果主 Redis 使用的是 6.0 引入的 ACL 用户，还需要通过 `masteruser` 指定用户名。

```conf
masterauth <master-password>
```

当从 Redis 失去了与主 Redis 的连接，或者主从同步正在进行中时，Redis 该如何处理外部发来的访问请求呢？这里，从 Redis 可以有两种选择：

- 第一种选择：如果 `replica-serve-stale-data` 设置为 `yes`（默认），则从 Redis 仍会继续响应客户端的请求，但返回的数据可能是过期的。
- 第二种选择：如果 `replica-serve-stale-data` 设置为 `no`，则从 Redis 会对客户端的请求返回“SYNC with master in progress”错误，当然也有例外，当客户端发来 `INFO`、`REPLICAOF` 等少数命令时，从 Redis 还是会进行处理。

可以控制一个从 Redis 是否可以接受写请求。将数据直接写入从 Redis，一般只适用于那些生命周期非常短的数据，因为在主从同步时，这些临时数据就会被清理掉。自从 Redis 2.6 版本之后，默认从 Redis 为只读。

```conf
replica-read-only yes
```

只读的从 Redis 并不适合直接暴露给不可信的客户端。为了尽量降低风险，可以使用 `rename-command` 指令来将一些可能有破坏力的命令重命名，避免外部直接调用（新版本更推荐使用 ACL，见下文“安全配置”）。比如：

```conf
rename-command CONFIG b8c02d524045429941cc15f59e41cb7be6c52
```

从 Redis 会周期性地向主 Redis 发出 PING 包。可以通过 `repl-ping-replica-period` 指令来控制其周期，默认是 10 秒。

```conf
repl-ping-replica-period 10
```

在主从同步时，可能在这些情况下会有超时发生：

1. 以从 Redis 的角度来看，当有大规模 IO 传输时；
2. 以从 Redis 的角度来看，当数据传输或 PING 时，主 Redis 超时；
3. 以主 Redis 的角度来看，在回复从 Redis 的 PING 时，从 Redis 超时。

用户可以设置上述超时的时限，不过要确保这个时限比 `repl-ping-replica-period` 的值要大，否则每次主 Redis 都会认为从 Redis 超时。

```conf
repl-timeout 60
```

我们可以控制在主从同步时是否禁用 `TCP_NODELAY`。如果设置为 `yes`（即禁用 `TCP_NODELAY`），那么主 Redis 会使用更少的 TCP 包和更少的带宽来向从 Redis 传输数据，但是这可能会增加一些同步的延迟，在 Linux 默认配置下大概会达到 40 毫秒左右。如果设置为 `no`，那么数据同步的延迟时间会降低，但是会消耗更多的带宽。

```conf
repl-disable-tcp-nodelay no
```

我们还可以设置同步队列长度。队列长度（backlog）是主 Redis 中的一个缓冲区，在与从 Redis 断开连接期间，主 Redis 会用这个缓冲区来缓存应该发给从 Redis 的数据。这样的话，当从 Redis 重新连接上之后，就不必重新全量同步数据，只需要同步这部分增量数据即可。

```conf
repl-backlog-size 1mb
```

如果主 Redis 等了一段时间之后，还是没有任何从 Redis 连接上来，那么缓冲队列中的数据将被清理掉。我们可以设置主 Redis 要等待的时间长度。如果设置为 0，则表示永远不清理。默认是 1 个小时。

```conf
repl-backlog-ttl 3600
```

我们可以给众多的从 Redis 设置优先级，在主 Redis 持续工作不正常的情况下，优先级高的从 Redis 将会被 Sentinel 升级为主 Redis。而编号越小，优先级越高。比如一个主 Redis 有三个从 Redis，优先级编号分别为 10、100、25，那么编号为 10 的从 Redis 将会被首先选中升级为主 Redis。当优先级被设置为 0 时，这个从 Redis 将永远也不会被选中。默认的优先级为 100。

```conf
replica-priority 100
```

假如主 Redis 发现延迟不超过 M 秒的从 Redis 少于 N 个，那么主 Redis 就停止接受外来的写请求。这是因为从 Redis 一般会每秒钟都向主 Redis 发出 PING，而主 Redis 会记录每一个从 Redis 最近一次发来 PING 的时间点，所以主 Redis 能够了解每一个从 Redis 的运行情况。

```conf
min-replicas-to-write 3
min-replicas-max-lag 10
```

上面这个例子表示，假如延迟小于等于 10 秒的从 Redis 不足 3 个，那么主 Redis 就不再接受外部的写请求。上述两个配置中有一个被置为 0，则这个特性将被关闭。默认情况下 `min-replicas-to-write` 为 0，而 `min-replicas-max-lag` 为 10。

# 4 安全配置

我们可以要求 Redis 客户端在向 Redis Server 发送请求之前，先进行密码验证。由于 Redis 性能非常高，按新版本配置文件的说法，在现代机器上每秒钟可以完成多达 100 万次的密码尝试（旧版本文档中为 15 万次），所以最好设置一个足够复杂的密码，否则很容易被黑客破解。

```conf
requirepass chenlongfei
```

这里通过 `requirepass` 将密码设置成我的名字（仅作演示，生产环境请使用足够长的随机密码）。

6.0 起 Redis 引入了 ACL（Access Control List，访问控制列表），`requirepass` 实际上只是为默认用户 `default` 设置密码的兼容写法。通过 ACL 可以创建多个用户，并分别限制每个用户可执行的命令和可访问的键，例如：

```conf
user admin on >StrongPassword ~* &* +@all
user app on >AppPassword ~app:* +@read +@write -@dangerous
```

也可以通过 `aclfile` 指定单独的 ACL 文件来管理用户。

Redis 允许我们对 Redis 命令进行更名，比如将一些比较危险的命令改个名字，避免被误执行。比如可以把 `CONFIG` 命令改成一个很复杂的名字，这样可以避免外部的调用，同时还可以满足内部调用的需要：

```conf
rename-command CONFIG b840fc02d5240454299c15f59e41cb7be6c89
```

我们甚至可以禁用掉 `CONFIG` 命令，那就是把 `CONFIG` 的名字改成一个空字符串：

```conf
rename-command CONFIG ""
```

但需要注意的是，如果使用 AOF 方式进行数据持久化，或者需要与从 Redis 进行通信，那么更改命令的名字可能会引起一些问题。新版本的 `redis.conf` 已将 `rename-command` 标记为“已废弃”（DEPRECATED），建议改用 ACL 把危险命令从默认用户中移除，只授予专门的管理员用户。

# 5 限制配置

我们可以设置 Redis 同时可以与多少个客户端进行连接，默认情况下为 10000 个客户端。如果 Redis 无法把进程的文件句柄上限调整到所需的值，就会把最大客户端数设置为当前的文件句柄限制值减去 32，因为 Redis 会为自身内部处理逻辑留一些句柄出来。

如果达到了此限制，Redis 则会拒绝新的连接请求，并且向这些连接请求方发出“max number of clients reached”以作回应。

```conf
maxclients 10000
```

我们甚至可以设置 Redis 可以使用的内存量。一旦到达内存使用上限，Redis 将会试图移除内部数据，移除规则可以通过 `maxmemory-policy` 来指定。

如果 Redis 无法根据移除规则来移除内存中的数据，或者我们设置了“不允许移除”，那么 Redis 则会针对那些需要申请内存的命令返回错误信息，比如 `SET`、`LPUSH` 等。但是对于无内存申请的命令，仍然会正常响应，比如 `GET` 等。

```conf
maxmemory <bytes>
```

需要注意的一点是，如果 Redis 是主 Redis（说明 Redis 有从 Redis），那么在设置内存使用上限时，需要在系统中留出一些内存空间给从 Redis 的输出缓冲区，只有在设置的是“不移除”的情况下，才不用考虑这个因素。

对于内存移除规则来说，Redis 提供了 8 种移除规则（4.0 起新增了两种 LFU 规则）。它们是：

1. `volatile-lru`：在设置了过期时间的 key 中，使用近似 LRU 算法移除 key；
2. `allkeys-lru`：在所有 key 中，使用近似 LRU 算法移除 key；
3. `volatile-lfu`：在设置了过期时间的 key 中，使用近似 LFU 算法移除 key（4.0 起）；
4. `allkeys-lfu`：在所有 key 中，使用近似 LFU 算法移除 key（4.0 起）；
5. `volatile-random`：在设置了过期时间的 key 中随机移除 key；
6. `allkeys-random`：在所有 key 中随机移除 key；
7. `volatile-ttl`：移除那些 TTL 值最小的 key，即那些最快将要过期的 key；
8. `noeviction`：不进行移除，针对写操作，只是返回错误信息。

其中 LRU 指最近最少使用（Least Recently Used），LFU 指最不经常使用（Least Frequently Used）。另外，8.6 的配置文件中又新增了 `volatile-lrm` 和 `allkeys-lrm` 两种规则，LRM 指最近最少修改（Least Recently Modified），只有写操作才会更新其时间戳，适合淘汰“很久没被更新、但可能仍被频繁读取”的 key。

无论使用上述哪一种移除规则，如果没有合适的 key 可以移除的话，Redis 都会针对写请求返回错误信息。

默认的移除规则为 `noeviction`：

```conf
maxmemory-policy noeviction
```

LRU、LFU 算法和最小 TTL 算法都并非是精确的算法，而是估算值，所以可以设置样本的大小。Redis 默认会检查 5 个 key 并选择其中最近最少使用的那个，可以通过下面的配置改变这个 key 样本的数量：设为 10 会非常接近真实的 LRU，但更耗 CPU；设为 3 则更快，但不太精确。

```conf
maxmemory-samples 5
```

# 6 AOF 配置

默认情况下，Redis 会异步地将数据持久化到磁盘。这种模式在大部分应用程序中已被验证是很有效的，但是在一些问题发生时，比如断电，则这种机制可能会导致数分钟的写请求丢失。

如《Redis 数据管理》一文的持久化部分中介绍的，AOF 是一种更好的保持数据一致性的方式。即使当服务器断电时，也仅会有 1 秒钟的写请求丢失，当 Redis 进程出现问题且操作系统运行正常时，甚至只会丢失一条写请求。

官方建议，AOF 机制和 RDB 机制可以同时使用，不会有任何冲突。AOF 默认是关闭的（`appendonly no`），需要手动开启：

```conf
appendonly yes
```

我们还可以设置 AOF 文件的名称：

```conf
appendfilename "appendonly.aof"
```

7.0 起 AOF 改为多文件（Multi Part AOF）机制：AOF 由一个基础文件（base）、若干增量文件（incr）和一个清单文件（manifest）组成，统一存放在 `dir` 下由 `appenddirname` 指定的目录中，`appendfilename` 只作为这些文件名的前缀。

```conf
appenddirname "appendonlydir"
```

`fsync()` 调用，用来告诉操作系统立即将缓存的命令写入磁盘。一些操作系统会“立即”进行，而另外一些操作系统则会“尽快”进行。

Redis 支持三种不同的模式：

1. `no`：不调用 `fsync()`，而是让操作系统自行决定 sync 的时间。这种模式下，Redis 的性能会最快。
2. `always`：在每次写请求后都调用 `fsync()`。这种模式下，Redis 会相对较慢，但数据最安全。
3. `everysec`：每秒钟调用一次 `fsync()`。这是性能和安全的折中。

默认情况下为 `everysec`。

```conf
appendfsync everysec
```

当 fsync 方式设置为 `always` 或 `everysec` 时，如果后台持久化进程需要执行一个很大的磁盘 IO 操作，那么 Redis 可能会在 `fsync()` 调用时卡住。目前尚未修复这个问题，这是因为即使我们在另一个新的线程中去执行 `fsync()`，也会阻塞住同步写调用。

为了缓解这个问题，我们可以使用下面的配置项，这样的话，当 `BGSAVE` 或 `BGREWRITEAOF` 运行时，`fsync()` 在主进程中的调用会被阻止。这意味着当另一个子进程正在进行保存时，Redis 的持久性就和设置了 `appendfsync no` 一样，在 Linux 默认设置下最坏可能丢失 30 秒的数据。如果 Redis 有时延问题，那么可以将下面的选项设置为 `yes`。否则请保持 `no`，因为这是保证数据完整性的最安全的选择。

```conf
no-appendfsync-on-rewrite no
```

我们允许 Redis 自动重写 AOF。当 AOF 增长到一定规模时，Redis 会隐式调用 `BGREWRITEAOF` 来重写日志文件，以缩减文件体积。

Redis 是这样工作的：Redis 会记录上次重写时的 AOF 大小。假如 Redis 自启动至今还没有进行过重写，那么启动时 AOF 文件的大小会被作为基准值。这个基准值会和当前的 AOF 大小进行比较。如果当前 AOF 大小超出所设置的增长比例，则会触发重写。另外还需要设置一个最小大小，是为了防止在 AOF 很小时就触发重写。

```conf
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
```

如果设置 `auto-aof-rewrite-percentage` 为 0，则会关闭此重写功能。

`aof-load-truncated` 指 Redis 在恢复时，是否忽略 AOF 末尾最后一条可能存在问题的命令，默认值为 `yes`。即在 AOF 写入时，可能存在命令写错的问题（比如突然断电，写了一半），这种情况下，`yes` 会记录日志并继续加载，而 `no` 会直接恢复失败，需要先用 `redis-check-aof` 修复。

```conf
aof-load-truncated yes
```

4.0 起还支持 RDB 与 AOF 混合持久化：重写 AOF 时，先以 RDB 格式写入当前数据快照作为文件开头，之后的增量命令再以 AOF 格式追加，这样既能加快重启加载速度，又保留了 AOF 的数据安全性。该选项在 5.0 起默认开启：

```conf
aof-use-rdb-preamble yes
```

# 7 Lua 脚本配置

Lua 脚本的最大执行时间，单位是毫秒。需要注意的是，脚本执行超过这个时间后，Redis 并不会自动终止它，而是开始对其他客户端的请求返回 `BUSY` 错误，此时只能使用 `SCRIPT KILL`（7.0 起的 Functions 对应 `FUNCTION KILL`）来终止尚未执行写操作的脚本；如果脚本已经执行过写命令，就只能用 `SHUTDOWN NOSAVE` 关闭服务器。7.0 起该配置项更名为 `busy-reply-threshold`，`lua-time-limit` 仍作为别名保留：

```conf
busy-reply-threshold 5000
```

如果此值设置为 0 或负数，则既不会有报错也不会有时间限制。

# 8 集群配置

平常的 Redis 实例不能作为集群的节点，只有作为集群节点启动的实例才可以。下面的配置可以使 Redis 实例作为集群节点启动：

```conf
cluster-enabled yes
```

每个集群节点都有一个集群配置文件，该文件是由集群节点来创建和维护的，不能人工参与。每个集群节点需要不同的配置文件，所以需要保证同一个系统下的集群节点没有重名的配置文件，建议以端口号标记配置文件。

```conf
cluster-config-file nodes-6379.conf
```

当节点超时大于 `cluster-node-timeout` 的时候，就会被认为宕机了，单位为毫秒。

```conf
cluster-node-timeout 15000
```

Redis 集群有一种 **failover（故障转移）机制**，即当主 Redis 宕机之后，会有一个最合适的从 Redis 充当主 Redis。但是，当从 Redis 的数据“太老”了，与主 Redis 的标准数据偏差很大，为了保证数据一致性，Redis 会放弃 failover。判别从 Redis 的数据是不是“太老”有两种方法：

1. 如果有多个从 Redis 可以接替主 Redis 的工作，则它们会交换信息，选取“最佳复制偏移”（接受了原主 Redis 最多的数据同步）的从 Redis 作为下一任主 Redis。
2. 每个从 Redis 计算与原主 Redis 最后一次数据同步的时间，当最短的时间间隔大于某个临界点的时候，集群则放弃 failover。

方法 2 当中的临界点可以通过配置调节，临界点的计算规则为：

`(node-timeout * cluster-replica-validity-factor) + repl-ping-replica-period`

如 `node-timeout` 为 30 秒，`cluster-replica-validity-factor` 为 10，`repl-ping-replica-period` 为 10 秒，当与原主 Redis 最后一次对话的时间间隔超过 310 秒的时候，集群就会放弃 failover。

当 `cluster-replica-validity-factor` 太大时，会使一台数据“太老”的从 Redis 充当主 Redis；而 `cluster-replica-validity-factor` 太小，可能会造成找不到合适的从 Redis 继任。如果设置为 0，则从 Redis 总会尝试接替主 Redis，不论数据新旧，以获得最大的可用性。

默认的 `cluster-replica-validity-factor` 为 10（5.0 之前写作 `cluster-slave-validity-factor`）。

```conf
cluster-replica-validity-factor 10
```

考虑一种情况：集群中某台主 Redis 的从 Redis 全部宕机了，它就成了没有可用从 Redis 的“孤立主节点”（orphaned master），一旦它自己再宕机就无法进行 failover。为此，Redis 集群支持从 Redis 自动迁移：其他从 Redis 较多的主 Redis 可以“匀”一个从 Redis 给孤立主节点。`cluster-migration-barrier` 规定了迁移的门槛：只有当原主 Redis 在迁移后仍至少保留这么多个可用的从 Redis 时，多出来的从 Redis 才会迁移过去。默认值为 1，即原主 Redis 至少还剩 1 个从 Redis 时才允许迁移。

```conf
cluster-migration-barrier 1
```

默认情况下，当集群检测到某个哈希槽（hash slot）没有被覆盖（没有任何节点为此服务）时会停止接受查询服务，如果集群部分宕机最终会导致整个集群不可用，当哈希槽重新被全覆盖的时候会自动变为可用。如果希望集群在部分哈希槽未被覆盖时，仍能对已覆盖的哈希槽继续提供查询服务，需要将 `cluster-require-full-coverage` 设置为 `no`。

```conf
cluster-require-full-coverage yes
```

# 9 慢日志配置

Redis 慢日志用于记录执行时间超过了指定时长的查询。这个时长不包括 IO 操作，比如与客户端的交互、发送响应内容等，而仅包括实际执行查询命令的时间。

针对慢日志可以设置两个参数，一个是执行时长，单位是微秒，另一个是慢日志的长度。执行时长的单位是微秒，即 1000000 表示一秒。负数则会禁用慢日志功能，而 0 则表示强制记录每一个命令。

```conf
slowlog-log-slower-than 10000
```

慢日志最大长度，可以随便填写数值，没有上限，但要注意它会消耗内存。当一个新的命令被写入日志时，如果日志已满，最老的一条会从命令日志队列中被移除。可以使用 `SLOWLOG RESET` 清空慢日志，以回收其占用的内存。

```conf
slowlog-max-len 128
```

# 10 延迟监控配置

Redis 的延迟监控子系统会在运行时对不同操作取样，以此来收集与延迟相关的数据，这些信息可以通过 `LATENCY` 命令以报表的形式呈现给用户。

系统只会记录那些执行时间等于或大于 `latency-monitor-threshold` 的操作（单位为毫秒），该值默认为 0，代表关闭监控，因为收集延迟数据多少会影响 Redis 的性能。

```conf
latency-monitor-threshold 0
```

# 11 事件通知配置

Redis 可以向客户端通知某些事件的发生。

例如，键空间（keyspace）事件通知如果开启，一个客户端对 Database 0 中的 `foo` 键执行了 `DEL` 操作，两条信息会通过 Pub/Sub 发布出去：

```text
PUBLISH __keyspace@0__:foo del
PUBLISH __keyevent@0__:del foo
```

可以选择需要发送哪种类型的通知，每种类型用一个字母代表：

- `K`：键空间事件，发布到 `__keyspace@<db>__` 前缀的频道；
- `E`：键事件，发布到 `__keyevent@<db>__` 前缀的频道；
- `g`：通用事件，比如 `DEL`、`EXPIRE`、`RENAME` 等操作都属于；
- `$`：String 操作；
- `l`：List 操作；
- `s`：Set 操作；
- `h`：Hash 操作；
- `z`：Sorted Set 操作；
- `x`：过期操作；
- `e`：驱逐操作（因为内存不足数据被删除）；
- `t`：Stream 操作（5.0 起）；
- `d`：模块（Module）键类型事件；
- `n`：新建 key 事件（不包含在 `A` 中）；
- `m`：访问不存在的 key 事件（key-miss，不包含在 `A` 中）；
- `o`：key 被覆盖写入事件（8.2 起，不包含在 `A` 中）；
- `c`：key 的类型被改变事件（8.2 起，不包含在 `A` 中）；
- `A`：代表 `g$lshzxetd` 的组合，所以 `AKE` 可以代表除 `n`、`m`、`o`、`c` 以外的所有事件。

`notify-keyspace-events` 配置以上述的字母组合为参数，举例说明：

1. `notify-keyspace-events Elg`：当有 List 操作或通用操作时，发布通知到 `__keyevent@<db>__` 前缀的频道；
2. `notify-keyspace-events Ex`：当有键的过期操作时，发布通知到 `__keyevent@0__:expired` 频道。

默认情况下，`notify-keyspace-events` 的参数为空字符串，代表关闭通知。

```conf
notify-keyspace-events ""
```

# 12 高级配置

> 说明：7.0 起，Redis 用 listpack 全面取代了 ziplist，相关配置项中的 `ziplist` 统一改为 `listpack`（如 `hash-max-ziplist-entries` → `hash-max-listpack-entries`），旧名称仍作为别名保留。下文统一使用新名称。

Hash 在条目数量较小的时候会使用一种高效的内存数据结构编码（listpack），当超过某个临界点就会采用另一种存储方式（哈希表），该临界点由下面的两个配置决定：

```conf
hash-max-listpack-entries 512
hash-max-listpack-value 64
```

与 Hash 类似，较小的 List 也会以一种特殊的编码方式来节省空间。3.2 起 List 统一采用 quicklist（由多个小的 ziplist/listpack 节点组成的双向链表）实现，原来的 `list-max-ziplist-entries`、`list-max-ziplist-value` 已被移除，改为用下面的配置控制每个节点的大小：取负数时表示按字节限制，`-2` 即每个节点不超过 8 KB；取正数时表示每个节点最多存放的元素个数。`list-compress-depth` 则控制链表两端各有多少个节点不压缩，0 表示不压缩。

```conf
list-max-listpack-size -2
list-compress-depth 0
```

Set 只有在满足下面的条件时才会采用 intset 编码：Set 中存储的恰好都是十进制的整数，而且长度不超过 64 位（有符号）。数量上限为：

```conf
set-max-intset-entries 512
```

7.2 起，元素较少、但不全是整数的小 Set 也可以使用 listpack 编码：

```conf
set-max-listpack-entries 128
set-max-listpack-value 64
```

同样，有序集合也会采用特殊编码来节省空间，只要不超过上限：

```conf
zset-max-listpack-entries 128
zset-max-listpack-value 64
```

Redis HyperLogLog 是用来做基数统计的算法，HyperLogLog 的优点是，在输入元素的数量或者体积非常非常大时，计算基数所需的空间总是固定并且很小的。当 HyperLogLog 用稀疏式表示法时所用内存超过下面的限制，就会转换成稠密式表示，为了更高的内存利用率，官方建议值为 3000。

```conf
hll-sparse-max-bytes 3000
```

Redis 在每 100 毫秒时使用 1 毫秒的 CPU 时间来对 Redis 的 hash 表进行重新 hash。当使用场景中有非常严格的实时性需要，不能够接受 Redis 时不时地对请求有 2 毫秒的延迟的话，把这项配置为 `no`。

如果没有这么严格的实时性要求，可以设置为 `yes`，以便能够尽可能快地释放内存。

```conf
activerehashing yes
```

客户端的输出缓冲区的限制，可用于强制断开那些因为某种原因从服务器读取数据的速度不够快的客户端（一个常见的原因是一个发布/订阅客户端消费消息的速度无法赶上生产它们的速度）。

可以对三种不同的客户端分别进行设置：

1. `normal`：正常客户端；
2. `replica`：从 Redis 和 `MONITOR` 客户端（5.0 之前写作 `slave`）；
3. `pubsub`：至少订阅了一个 Pub/Sub 频道（channel）或模式（pattern）的客户端。

每个 `client-output-buffer-limit` 的语法为：

```conf
client-output-buffer-limit <class> <hard limit> <soft limit> <soft seconds>
```

一旦达到硬限制，客户端会立即断开；或者达到软限制并连续保持了指定的秒数，客户端也会断开。

例如，如果硬限制为 32 MB、软限制为 16 MB/10 秒，那么当输出缓冲区的大小达到 32 MB 时，客户端将会立即断开；当客户端达到 16 MB 并且连续 10 秒都超过了限制，也将断开连接。

默认 `normal` 客户端不做限制，因为普通客户端只有在发出请求后才会收到数据（而不是由服务端主动推送），只有异步客户端才可能出现请求数据的速度比它读取的速度还快的情况。

把硬限制和软限制都设置为 0 来禁用该特性：

```conf
client-output-buffer-limit normal 0 0 0
client-output-buffer-limit replica 256mb 64mb 60
client-output-buffer-limit pubsub 32mb 8mb 60
```

Redis 会按照一定的频率来执行后台任务，比如关闭超时的客户端、清除过期键等。不是所有的任务都会按照相同的频率来执行，但 Redis 依照指定的 `hz` 值来执行检查任务。5.0 起还新增了 `dynamic-hz`（默认 `yes`），会在客户端连接较多时自动调高实际的 hz 值。

```conf
hz 10
```

AOF 重写过程中，是否采取增量文件同步策略，默认为 `yes`。开启后，重写过程中每生成 4 MB 数据就进行一次文件同步（早期版本为 32 MB），这样可以把数据更平滑地提交到磁盘，避免一次性写入大文件造成较大的延迟抖动。RDB 保存时也有对应的 `rdb-save-incremental-fsync` 配置项。

```conf
aof-rewrite-incremental-fsync yes
```

# 13 其他新版本配置

除了上面这些，较新版本还增加了一些常用的配置项，这里简单列举两类：

一类是 4.0 引入的惰性删除（lazy free）：开启后，淘汰、过期、服务端内部删除等场景下对大 key 的释放会交给后台线程完成，避免阻塞主线程。在 8.2 的配置文件中，它们默认都为 `no`：

```conf
lazyfree-lazy-eviction no
lazyfree-lazy-expire no
lazyfree-lazy-server-del no
replica-lazy-flush no
lazyfree-lazy-user-del no
lazyfree-lazy-user-flush no
```

另一类是 6.0 引入的 I/O 多线程 `io-threads`：默认为 1，即只使用主线程；设置为大于 1 的值后，会使用多个线程处理网络读写，但命令本身仍由主线程单线程执行。一般只在确实遇到网络 I/O 瓶颈时才需要开启（具体线程数建议需核实）。

```conf
io-threads 4
```

# 14 小结

`redis.conf` 中的配置项很多，但大部分保持默认即可。实际使用中最常调整的是网络与安全（`bind`、`protected-mode`、`requirepass`/ACL）、内存与淘汰策略（`maxmemory`、`maxmemory-policy`）、持久化（`save`、`appendonly`、`appendfsync`）以及主从和集群相关的几项。由于不同版本的配置项名称和默认值差异较大，修改前最好以所用版本自带的 `redis.conf` 注释为准，也可以通过 `CONFIG GET <parameter>` 查看当前生效的值。
